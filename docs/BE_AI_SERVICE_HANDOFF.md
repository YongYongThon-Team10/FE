# BE 전달: 질문 분석, 선호도 기반 추천, 혼잡도 AI 연동

작성일: 2026-11-15. FE에서 구현한 화면과 요청 형식을 기준으로 정리한 BE 작업 요청서다. 개발 브랜치 검토용이며 운영 반영은 별도다.

## 1. 서비스 방향과 역할

사용자는 마이페이지에서 카테고리 관심도, 음식 취향과 카페 특징을 선택한다. 질문의 명시 조건을 먼저 적용하고, 사용자의 선호도, 주변 후보의 별점과 리뷰, 거리 및 예상 혼잡도를 종합해 추천한다. OpenAI는 다음 세 작업에서 사용한다.

| 구분        | OpenAI 역할                                                      | 서버가 책임질 계산 및 검증                                |
| ----------- | ---------------------------------------------------------------- | --------------------------------------------------------- |
| 질문 분석   | 자연어를 날짜, 지역, 음식 종류, 카페 특징 등의 조건으로 변환     | 허용 값, 날짜, 위치, 요청에 실제로 있는 조건 검증         |
| 추천 판단   | 확보한 후보와 리뷰에서 취향 적합성 판단, 후보별 보정과 근거 선택 | 후보 ID 제한, 반경과 명시 조건 필터, 점수 합산, 출처 보존 |
| 혼잡도 판단 | 공공데이터 및 관측값을 바탕으로 예상 유입과 유출 판단            | 체류 인원과 점유율, 등급 계산, 인원 보존과 예측 범위 검증 |

OpenAI는 실시간 장소 검색기나 방문객 센서가 아니다. 현재 데이터는 수집 API 및 DB가 공급하고, AI가 그 입력 안에서 판단해야 한다. 없는 별점, 리뷰, 수용인원이나 실측 인구를 생성하지 않는다.

## 2. 현재 구현과 추가 작업 구분

| 항목                | 상태                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| 기존 BE 질문 분석   | SearchService가 OpenAiClient.completeJson을 사용. POST /api/search/parse                                   |
| 기존 BE 장소 검색   | PlaceService가 카카오 로컬 키워드 API 사용. 별점과 리뷰는 제공하지 않음                                    |
| 앞선 로컬 BE 혼잡도 | BE/crowding 도메인에 목업과 OpenAI 연동 구현. 고정 시연 시각만 지원. GitHub에 반영된 상태로 간주하지 말 것 |
| FE 마이페이지       | /#/mypage. 카테고리 6개, 음식 및 카페 취향, 별점 중요도, 혼잡 회피 설정                                    |
| FE 선호도 저장      | 계정별 또는 guest별 브라우저 저장. 알림 설정과 별도 데이터                                                 |
| FE 맞춤 추천        | /#/recommendations. 취향, 질문, 반경, 리뷰와 혼잡도 반영. 주변 맛집과 카페로 이동                          |
| FE 시연             | 목업 장소 10개와 별점, 리뷰. 수용인원 기반 혼잡도 3곳. 5초 간격으로 4개 시연 시각 재생                     |
| FE 서버 연결        | 아래 4개 신규 또는 기존 API 어댑터 준비. 정기 조회, 탭 복귀, 온라인 복구와 취소 처리                       |
| BE 신규 필요        | POST /api/recommendations, GET/PUT /api/me/preferences. 실제 공급자, 리뷰 보강, 추천 AI 구현               |

현재 FE의 mock 모드는 실제 OpenAI를 호출하지 않는다. 질문 해석과 AI 보정도 영상 재현용 예시이며 화면과 응답 메타데이터에 표시한다. 실제 AI 시연은 BE 구현을 연결한 api 모드에서 수행한다.

기존 홈의 대표 명소와 기존 코스의 거리순 후보는 탐색 기능으로 유지한다. 이번 맞춤 추천 화면이 별점과 리뷰 기반 개인화 흐름을 담당한다. 두 결과를 동일한 AI 결과로 표시하지 않는다.

## 3. 요청 처리 순서

1. 사용자 입력, 방문 시각, 기준 좌표와 반경을 검증한다.
2. 질문이 있으면 SearchService 또는 별도 QueryIntentService로 분석한다. 날짜와 위치는 기존 서버 규칙으로 보정한다. 빈 질문이면 생략한다.
3. 현재 질문의 명시 조건을 적용한다. 선호도는 기본 순위 가중치이며, 관심도 0은 제외가 아니라 낮은 관심이다.
4. 장소 공급자로 반경 안의 관광지, 공원, 음식점과 카페 후보를 확보한다.
5. 리뷰 공급자로 별점, 리뷰 수와 허용된 리뷰 텍스트를 보강한다. 서로 다른 공급자 ID는 같은 가게로 확인한 경우만 연결한다.
6. 장소별 수용인원, 과거 방문 패턴, 행사 및 사용 가능한 현재 관측값을 수집한다.
7. CrowdingService가 현재 및 미래 혼잡도를 계산한다. 관측값이 없는 가게는 혼잡도 null을 허용한다.
8. RecommendationService가 기본 점수를 계산하고, OpenAiClient를 통해 제한된 후보의 순위 보정과 근거를 판단한다.
9. AI 결과를 검증하고 최종 점수 및 출처를 반환한다.
10. FE는 응답의 sourceAsOf와 generatedAt을 구분하고, 조회 실패 시 최신 결과로 표시하지 않는다.

기존 E4의 응답에는 음식 종류와 카페 특징이 없으므로 추천용 내부 Intent DTO에 requestedCategories, cuisines, cafeFeatures를 추가해야 한다. 날짜, 지역 등 기존 조건을 보존하고 명시되지 않은 특징은 빈 배열로 둔다. 질문 분석을 FE와 BE에서 중복 호출하지 않고 추천 API 안에서 조합한다.

## 4. 마이페이지 선호도 계약

```http
GET /api/me/preferences
PUT /api/me/preferences
Authorization: Bearer <access-token>
```

PUT 요청과 GET 및 PUT 성공 응답의 data는 같은 구조다.

```json
{
  "schemaVersion": 1,
  "categoryWeights": {
    "park": 5,
    "food": 4,
    "cafe": 5,
    "culture": 3,
    "sports": 1,
    "shopping": 2
  },
  "cuisines": ["korean", "light"],
  "cafeFeatures": ["quiet", "view"],
  "ratingPriority": 3,
  "avoidCrowds": true,
  "updatedAt": "2026-11-15T14:00:00+09:00"
}
```

1. 관심도와 별점 중요도는 0~5 정수다. 카테고리 6개는 모두 포함한다.
2. cuisines 허용 값: korean, japanese, western, light.
3. cafeFeatures 허용 값: quiet, dessert, view, spacious.
4. 첫 조회는 카테고리 모두 3, 배열 비어 있음, ratingPriority 3, avoidCrowds true, updatedAt null을 반환한다.
5. updatedAt은 저장 시 서버 시각으로 확정한다.
6. 사용자 ID는 요청에서 받지 않고 인증 주체로 결정한다. 사용자별 DB 저장 및 다른 계정 조회와 수정 차단이 필요하다.
7. FE는 브라우저 저장 후 api 모드에서 로그인 사용자만 PUT 동기화를 수행한다. 서버 실패를 계정 저장 성공으로 안내하지 않는다. 계정 선호도 불러오기 버튼은 GET을 호출한다.
8. 게스트는 브라우저 프로필을 추천 요청에 전달한다. 계정 로그인 시 게스트 선호도를 다른 계정에 자동 덮어쓰지 않는다.

## 5. 추천 요청 계약

```http
POST /api/recommendations
Content-Type: application/json
Authorization: Bearer <access-token, 로그인한 경우만>
```

게스트도 요청할 수 있다. FE가 명시적으로 전달한 profile을 이번 추천의 기준으로 사용한다. profile을 계정 DB에 자동 저장하지는 않는다.

```json
{
  "query": "조용한 카페와 한식 맛집",
  "profile": {
    "schemaVersion": 1,
    "categoryWeights": {
      "park": 5,
      "food": 4,
      "cafe": 5,
      "culture": 3,
      "sports": 1,
      "shopping": 2
    },
    "cuisines": ["korean"],
    "cafeFeatures": ["quiet"],
    "ratingPriority": 3,
    "avoidCrowds": true,
    "updatedAt": null
  },
  "center": { "lat": 37.2411, "lng": 127.1776 },
  "radiusMeters": 3000,
  "categories": ["food", "cafe"],
  "visitAt": "2026-11-21T14:10:00+09:00"
}
```

1. query는 빈 값 허용, 최대 200자다.
2. center는 유효한 위경도, 반경은 우선 1km, 3km, 5km를 지원한다. categories가 빈 배열이면 전체 카테고리다.
3. FE의 api 모드는 재조회할 때 visitAt을 현시각으로 갱신한다. mock 모드는 지정된 시연 시각을 사용한다.
4. 좌표가 없으면 임의로 주변 후보라고 주장하지 않는다. FE 기본 위치는 용인시청 인근이며 화면에 기준 위치를 표시한다.
5. 질문과 선택 필터가 충돌하면 AI가 몰래 무시하지 않고 조건을 안내하거나 빈 결과를 반환한다.

## 6. 추천 점수와 AI 결과

초기 점수식은 FE mock과 동일한 형태로 시작한다. 실제 정답으로 검증한 가중치가 아니다.

```text
P = 카테고리 관심도 / 5 * 100
Q = ((별점 * 리뷰 수 + 3.8 * 30) / (리뷰 수 + 30)) / 5 * 100
R = 일치하는 리뷰 특징 수 / 요청 및 선호 특징 수 * 100
D = max(0, 1 - 거리 / 반경) * 100
C = max(0, 100 - 예상 점유율)

가중치:
P: 0.40
Q: ratingPriority * 0.04
R: 0.15
D: 0.15
C: avoidCrowds가 true면 0.10, 아니면 0

기본 점수 = 사용 가능한 신호의 가중합 / 사용 가능한 가중치 합
최종 점수 = clamp(기본 점수 + AI 보정, 0, 100)
AI 보정 범위 = -10~+10
```

1. 별점이나 리뷰 수 중 하나라도 미확인이면 rating은 null로 반환한다. 모르는 리뷰 수를 0으로 만들지 않는다.
2. 리뷰 또는 혼잡도가 없으면 해당 신호를 0점으로 넣지 않고 분모의 가중치에서도 제외한다. missingSignals에 남긴다.
3. 3.8과 30은 시연용 별점 사전값이다. 같은 별점 척도 안에서 리뷰가 적은 후보의 극단값을 완화하려는 값이며 실제 운영 자료로 보정해야 한다.
4. 별점 공급자마다 척도와 표본이 달라 원시 별점을 무조건 섞지 않는다. FE 계약은 5점 척도다.
5. 쾌적 수용인원 기준이 다른 장소의 점유율 비교는 검증이 필요하다. C는 초기 추천 휴리스틱이다.
6. 명시 조건과 거리 필터는 AI 보정 전에 적용하고 AI가 이를 무효화할 수 없다.

추천 AI 입력은 후보 ID, 기본 점수, 프로필, 분석한 질문, 별점과 리뷰 수, 허용된 리뷰 근거, 거리와 혼잡도다. OpenAiClient에는 다음처럼 제한된 JSON을 요청한다.

```json
{
  "judgments": [
    {
      "candidateId": "provider:123",
      "adjustment": 6,
      "reasonCodes": ["PREFERENCE_MATCH", "REVIEW_FEATURE_MATCH"],
      "evidenceIds": ["review_summary:123", "profile:cafeFeatures"]
    }
  ]
}
```

서버는 존재하지 않는 ID, 중복 ID, 범위 밖 보정, 제공하지 않은 evidenceId 및 지원하지 않는 근거 코드를 거부한다. 리뷰 원문은 데이터로만 취급하며 그 안의 지시문을 실행하지 않는다. 사용자 설명은 검증된 근거와 숫자로 만든다. AI가 영업 여부, 별점이나 실제 방문자 수를 새로 선언하게 하지 않는다.

AI 실패 시 기본 점수로 정렬하고 rankingMethod=rule_fallback 및 warnings를 반환할 수 있다. 후보 수집 자체가 실패하면 정상 빈 목록이나 mock으로 바꾸지 말고 오류를 반환한다.

## 7. 추천 응답 계약

기존 성공 envelope를 유지한다. 아래는 전부 목업 입력에 실제 AI를 적용했을 때의 예시 구조이며 실제 운영 결과가 아니다.

```json
{
  "data": {
    "dataMode": "simulation",
    "queryMethod": "openai",
    "rankingMethod": "openai",
    "generatedAt": "2026-11-15T14:01:00+09:00",
    "sourceAsOf": "2026-11-21T14:10:00+09:00",
    "refreshAfterSeconds": 30,
    "items": [
      {
        "id": "demo_cafe_01",
        "name": "시연 고요카페",
        "category": "cafe",
        "address": "용인 지역 시연용 가상 장소",
        "location": { "lat": 37.242, "lng": 127.178 },
        "distanceMeters": 106,
        "detailUrl": null,
        "tags": ["quiet", "spacious"],
        "rating": {
          "value": 4.4,
          "count": 220,
          "source": "시연 별점",
          "asOf": "2026-11-21T14:10:00+09:00"
        },
        "review": {
          "summary": "조용한 분위기라는 시연 리뷰",
          "tags": ["quiet", "spacious"],
          "source": "시연 리뷰",
          "asOf": "2026-11-21T14:10:00+09:00"
        },
        "source": {
          "name": "시연 장소 데이터",
          "dataMode": "simulation",
          "fetchedAt": "2026-11-21T14:10:00+09:00"
        },
        "crowdingPlaceId": null,
        "crowding": null,
        "score": 100,
        "aiAdjustment": 6,
        "reasons": ["조용한 카페 선호와 제공된 리뷰 특징이 일치해요."],
        "missingSignals": ["crowding"]
      }
    ],
    "warnings": ["장소와 별점, 리뷰는 시연용 데이터입니다."]
  },
  "error": { "code": null, "message": null }
}
```

1. items는 최대 100개이며 score 내림차순으로 반환한다. 동점은 안정적인 ID 순서로 정렬한다.
   score는 후보 비교용 지수이며 예측 정확도나 확률이 아니다.
2. detailUrl은 HTTPS 또는 null이다. 후보 ID는 공급자 namespace를 포함해 충돌을 막는다.
3. category는 park, food, cafe, culture, sports, shopping 중 하나다.
4. dataMode는 simulation(입력이 목업), live(연동한 실제 입력), mixed(실제 입력과 목업 혼합)다. AI 예측이라는 이유만으로 simulation이 되는 것은 아니다.
5. 후보별 source.dataMode도 보존한다. 목업 신호가 섞인 후보를 live로 표시하지 않는다. FE는 live 응답에 simulation 후보나 혼잡도가 섞이면 거부한다.
6. queryMethod는 openai, scenario_mock, none 중 하나다. 빈 질문이면 none이다.
7. rankingMethod는 openai, scenario_mock, rule_fallback 중 하나다. scenario_mock은 실제 AI 호출을 의미하지 않는다.
8. generatedAt은 계산한 서버 시각, sourceAsOf는 추천에 사용한 데이터 묶음의 기준 시각이다. 개별 별점, 리뷰의 asOf와 후보 fetchedAt도 보존한다.
9. refreshAfterSeconds는 15~300초 범위다. 기본 30초이며 FE는 이를 따른다.

## 8. 혼잡도와 공공데이터 결합

기존 로컬 BE의 POST /api/crowding/estimate를 재사용한다. 요청은 `{placeId, at}`이며 FE가 혼잡도 상세를 누르면 호출한다. 추천 응답 items[].crowding에는 같은 응답 data를 포함할 수 있다. 상세 요청의 at은 추천 전체 시각 대신 해당 crowding.asOf를 우선 사용한다.

기존 목업 CrowdingService는 고정된 2026-11-21 14:10, 14:20, 14:30, 14:40만 입력으로 지원한다. 실시간 전환 시 공급자와 지원 시각 검증을 함께 확장해야 한다. FE에서 at만 now로 바꾸면 실시간 구현이 끝나는 것은 아니다.

```text
평소 유입 = 유사 날짜 하루 방문객 * 해당 구간 입장 비율 * 상황 보정
행사 추가 유입 = 행사 예상 방문객 * 구간 입장 비율 * 비중복 비율
AI 입력 = 평소 유입, 행사 추가 유입, 직전 체류, 평균 체류시간, 관측 신호
예상 체류 = 직전 체류 + 예상 유입 - 예상 유출
점유율 = 예상 체류 / 혼잡도 산정용 수용인원 * 100
```

1. 수용인원은 출처와 공간 범위가 확인된 쾌적 수용인원이다. 최대 안전 수용인원과 혼동하지 않는다.
2. 일일 누적 방문객을 현재 체류 인원으로 쓰지 않는다. 입장과 퇴장, 시간대별 체류를 구분한다.
3. 현재 체류 관측이 있으면 그것으로 현재값을 갱신하고 AI는 이후 유입과 유출을 예측한다.
4. 실측 입장 및 퇴장이 있으면 누적하고, 누락 구간만 AI로 보완한다.
5. 주차와 교통 같은 간접 관측은 검증한 전환 관계로 보정한다. 주변 도로 정체나 주차 차량을 공원 내부 인구로 그대로 치환하지 않는다.
6. 실제 관측이 없으면 과거 패턴과 행사 기반 예상값이라고 표시한다. 수용인원과 과거 패턴도 없으면 혼잡도 null과 정보 부족을 반환한다.
7. 행사 후보는 실제 개최일과 시간이 확인된 것만 반영한다. 여러 달짜리 등록 기간을 매일 개최로 해석하지 않는다.
8. 같은 행사와 기존 방문 수요를 중복 가산하지 않는다. 서로 겹치는 지역 인구도 단순 합산하지 않는다.
9. 음수, 소수 인원, 구간 누락, 이전 체류와 이어지지 않는 값, 허용 범위 밖 AI 출력을 거부한다. 수용인원 초과는 자르지 않는다.
10. 혼잡도 구간은 초기 40%, 65%, 85% 경계다. 실제 현장 정답으로 검증하기 전에는 confidence=low를 유지한다.
11. AI가 실패하면 기존 규칙 대체와 predictionSource, warnings를 유지한다. 실제 API 실패를 시연값으로 바꾸지 않는다.

혼잡도 data의 필수 구조는 placeId, dataMode, predictionSource, asOf, generatedAt, confidence, capacity, current, forecast, warnings다. current와 forecast는 at, previousPeople, inflowPeople, outflowPeople, estimatedPeople, occupancyPercent, level, label을 포함한다. forecast는 10분 간격 3개이며 이전 estimatedPeople이 다음 previousPeople과 같아야 한다. 기존 로컬 BE의 reasons, evidence 등 추가 필드는 유지할 수 있다.

카카오 로컬 문서의 장소 응답은 별점과 리뷰를 제공하는 계약이 아니다. 상세 웹페이지 주소가 있다는 이유로 별점과 리뷰까지 API로 받을 수 있다고 가정하면 안 된다. [카카오 로컬 공식 문서](https://developers.kakao.com/docs/ko/local/dev-guide)

Google Place Details(New)는 별점과 리뷰 정보를 제공하며 원하는 필드를 FieldMask로 지정한다. 비용과 표시 및 저장 조건을 확인하고 공급자로 연결한다. 반환 리뷰가 전체 리뷰를 대표한다고 단정하지 않는다. [Google Places 공식 문서](https://developers.google.com/maps/documentation/places/web-service/place-details)

관광지 기준 정보에는 면적, 수용인원수와 주차가능수 항목이 있다. 모든 공원을 포괄하거나 실시간 잔여 주차를 제공하는 것은 아니다. [전국관광지정보표준데이터](https://www.data.go.kr/data/15021141/standard.do)

권장 BE 인터페이스는 CandidateProvider, ReviewProvider, CrowdingDataProvider다. 공급자별 실제 API와 Mock 구현을 같은 DTO로 정규화한다. 위치와 상세 정보는 사용자 요청 시 갱신하고, 리뷰는 공급자 정책에 맞는 별도 주기로 갱신한다. FE의 30초 조회가 외부 리뷰 API를 30초마다 전부 호출한다는 뜻은 아니다.

## 10. 실시간 갱신, 비용과 장애

1. FE는 응답 완료 후 refreshAfterSeconds만큼 기다렸다가 재조회한다. 요청이 겹치면 이전 요청을 취소한다.
2. 탭 복귀와 온라인 복구 시 재조회하며, 화면 이탈 시 타이머와 요청을 해제한다.
3. BE는 원본 관측 시각을 보존한다. 캐시를 다시 읽은 시간을 새로운 관측 시각으로 덮어쓰지 않는다.
4. 질문 분석 캐시는 질문과 기준 날짜로, 추천 캐시는 프로필, 명시 조건, 위치 범위, 방문 구간 및 실제 입력 데이터 해시로 구분한다.
5. 같은 데이터의 재조회에는 검증한 AI 결과를 재사용할 수 있다. generatedAt 같은 출력 시각을 캐시 키에 넣어 매번 AI를 다시 호출하지 않는다.
6. 추천 내 후보별 혼잡도 조회는 병렬 처리 또는 배치 처리한다. 모델 호출은 무제한으로 후보마다 반복하지 않는다.
7. FE 추천 요청 제한은 65초, 혼잡도 상세는 25초다. 서버 전체 작업 예산은 이보다 짧게 설정한다.
8. 후기 데이터 미제공은 해당 필드 null, 후보 없음은 정상 items=[], 외부 후보 조회 실패는 오류로 구분한다.
9. FE는 같은 조건의 마지막 성공 결과만 오류 안내와 함께 유지한다. 질문, 위치나 프로필이 달라지면 이전 결과를 새 조건의 추천으로 표시하지 않는다.
10. 공개 추천 API에는 사용자 및 IP 단위 요청 제한, 요청 크기 제한과 후보 수 제한을 적용한다. 계정 선호도 API는 인증을 요구한다.

## 11. FE 설정과 시연 흐름

```dotenv
# 영상 재현. 실제 OpenAI 호출 없음
VITE_INTELLIGENCE_MODE=mock

# BE의 추천 API 구현 후 실제 호출할 때
# VITE_INTELLIGENCE_MODE=api
# VITE_TEAM_API_BASE_URL=https://your-backend.example.com
```

OpenAI 및 외부 REST 비밀 키를 VITE_ 환경변수에 넣지 않는다. BE 환경설정에만 보관한다. FE 연결 모드는 빌드 시 결정되므로 변경 후 개발 서버 재시작 또는 재빌드가 필요하다.

1. 홈의 취향 맞춤 추천 보기 또는 마이페이지 링크를 연다.
2. 마이페이지에서 카페 관심도와 조용한 분위기 등을 선택해 저장한다.
3. 맞춤 추천에서 질문, 유형과 반경을 적용하고 추천 근거, 별점과 리뷰를 확인한다.
4. 관광지 카드의 주변 맛집과 카페로 기준 위치를 바꿔 추천한다.
5. 시연 호수공원의 혼잡도 자세히를 눌러 수용인원, 유입과 유출 및 미래 예측을 확인한다.
6. 5초 간격 시연 재생으로 14:10부터 14:40까지 혼잡도 변화와 재추천을 보여준다.

## 12. BE 완료 확인 기준

1. 질문 분석, 추천과 혼잡도에서 OpenAI 호출 여부를 각각 응답에 표시한다.
2. 서로 다른 계정의 선호도가 섞이지 않고, 게스트 프로필도 추천에 전달된다.
3. 같은 조건에서 프로필을 바꾸면 해당 취향과 근거가 추천에 반영된다.
4. 추천 대상은 실제 공급 후보 ID 안에 있으며 반경과 명시 조건을 벗어나지 않는다.
5. 별점과 리뷰가 없을 때 null을 유지하고 실제 값을 생성하지 않는다.
6. 혼잡도에서 수용인원, 유입, 유출, 체류와 점유율의 계산이 맞는다.
7. 목업 입력 + 실제 AI, 목업 입력 + 고정 시나리오, 실제 입력 + AI를 구분한다.
8. 실제 공급자 실패를 목업 데이터로 감추지 않는다.
9. FE가 이 문서의 응답을 수정 없이 파싱하고 최신 시각 및 장애 상태를 표시한다.
10. 로컬 API 및 FE 검증 후 사용자가 검토하고 GitHub 반영한다.

## 13. FE 로컬 검증 결과

2026-11-15 기준 정적 검사(lint, typecheck, format), 프로덕션 빌드, 카카오 프록시 테스트 6개와 전체 Playwright 테스트 73개가 통과했다. 신규 검증은 선호도 저장과 재적용, 질문 및 리뷰 기반 순위, 혼잡도 인원 보존, 목업 시각 변경, API 전송, 실패 시 목업 미대체, 정기 재조회와 화면 이탈 시 중단을 포함한다. 실제 신규 BE API나 OpenAI 계정 성공을 검증했다는 의미는 아니다.

기존 5173 포트에 다른 설정의 개발 서버가 실행 중이라 시연 지도 테스트는 별도 포트를 사용했다. 기존 개발 서버를 종료하거나 설정을 바꾸지 않았다. 같은 환경에서는 다음처럼 실행한다.

```powershell
$env:PLAYWRIGHT_DEMO_PORT = '5183'
npm test -- --workers=2
```
